# Frameworks, Implementation, and Reproducibility

Don't hand-roll a simulator unless you have a strong reason. Maintained frameworks
give you a scheduler, spatial/network structures, batch-running, visualization,
and a community that has already hit the bugs you're about to. Choose by language,
scale, and audience.

2. The main frameworks

## 1. Choosing a framework

Decision drivers, in rough priority:

- **Audience and shareability.** If non-programmers (students, stakeholders,
  reviewers) must read, run, or tinker with the model, NetLogo's low barrier and
  built-in GUI win. If it lives inside a data/ML pipeline, a Python or Julia
  framework fits.
- **Language you and your team already use.** A model that gets maintained beats a
  faster one that doesn't.
- **Scale.** Thousands–hundreds of thousands of agents: NetLogo/Mesa are usually
  fine. Millions of agents or large sweeps: reach for HPC/GPU frameworks.
- **Performance ceiling.** Interpreted environments (NetLogo, Python/Mesa) trade
  speed for ease; compiled (Java MASON/Repast, Julia Agents.jl, C++ RepastHPC,
  GPU FLAME GPU) trade ease for speed.

A common and sensible pattern: **prototype in NetLogo or Mesa** to get the model
and ODD right, then port to a faster framework only if compute becomes the binding
constraint.

## 2. The main frameworks

**NetLogo.** The de facto teaching and rapid-prototyping standard; free,
cross-platform, gentle learning curve, excellent built-in visualization. Ships
with **BehaviorSpace** for automated parameter sweeps and a large Models Library.
Pairs directly with the Railsback & Grimm textbook. Best default for learning,
communication, and most small-to-medium scientific models. Limits: slower at large
scale, less convenient inside larger software/data pipelines (though it has a
controlling API and an R/Python bridge).

**Mesa (Python).** The Python-native option; aims to be the NetLogo/Repast/MASON
alternative for the Python ecosystem. Built-in spatial grids/continuous space,
schedulers, a browser-based and Jupyter-friendly visualization layer, and
`batch_run` for experiments. Strongest when you want results to flow straight into
pandas/NumPy/scikit-learn or ML tooling. Actively developed (Mesa 3.x, with 4.x in
progress). Performance is Python-bound; vectorize or drop to compiled extensions
for heavy models.

**Repast (Repast Simphony / RepastHPC).** Mature, feature-rich Java/Groovy suite
(Simphony) with a high-performance C++ sibling (**RepastHPC**) for clusters. Good
for large, serious models needing GIS integration and HPC scaling; steeper
learning curve than NetLogo/Mesa.

**MASON (Java).** Fast, lightweight Java library with a distributed extension for
parallel/HPC runs; favored when raw Java speed and embeddability matter and you
don't need NetLogo-style hand-holding.

**Agents.jl (Julia).** Modern, high-performance framework that approaches
compiled-language speed while keeping high-level ergonomics; attractive when you
need both speed and expressive code, and increasingly popular for
computationally heavy research models.

**FLAME GPU.** Specialized for massive agent populations on GPUs; the choice when
you have millions of agents and the model maps to GPU parallelism. Requires
extended expertise.

Rule of thumb (from comparative reviews): when performance is critical and HPC is
available, **FLAME GPU, RepastHPC, and distributed MASON** are the top performers
but demand the most expertise; **NetLogo and Mesa** maximize accessibility and
development speed for the large majority of models.

## 3. Reproducibility practices (non-negotiable)

ABM has a real replication problem; disciplined practice is the fix. For any model
that produces results someone might cite or rely on:

- **Fix and report the random seed(s).** Make any single run exactly reproducible,
  and record the seed alongside the output.
- **Separate parameters from code.** Keep parameter values in config/data files,
  not buried in source, so a run is fully specified by code + config + seed.
- **Document in ODD** (and TRACE for decision-support models) so the model is
  reproducible from text, not just from code. See `odd-protocol.md`.
- **Version-control everything** — model code, parameter files, analysis scripts —
  and tag the exact commit used for published results.
- **Archive in a model repository.** CoMSES Net / OpenABM (comses.net) provides
  peer review, DOIs, and reproducibility standards for ABMs; deposit there.
- **Script the whole pipeline** from raw runs to figures, so the analysis is
  rerunnable end-to-end, not assembled by hand.
- **State the environment** (framework version, language version, OS) — behavior
  can differ across versions.

A model whose results can't be regenerated by an independent person from the
shared artifacts is, for scientific purposes, unfinished.

## 4. Performance practices

When runs are too slow for the calibration/SA you need:

- **Profile before optimizing** — find the actual hot loop; it's often agent
  neighbor-lookup or unnecessary global scans.
- **Reduce complexity to purpose** (KISS) before reaching for more hardware — the
  cheapest speedup is the rule you didn't need.
- **Exploit framework features** — spatial indexing, agent sets/queries, and
  vectorized operations instead of per-agent Python loops; NetLogo-specific speed
  guidance exists (Railsback et al. 2017).
- **Parallelize across runs, not just within them** — replications and
  parameter-sweep points are embarrassingly parallel; batch-runners exploit this.
- **Emulate** — replace the expensive model with a fast statistical surrogate for
  calibration and global sensitivity analysis (see `validation-and-calibration.md`).
- **Escalate hardware last** — move to compiled/HPC/GPU frameworks once the model
  and experiment design are stable, since porting has its own cost and artefact risk.
