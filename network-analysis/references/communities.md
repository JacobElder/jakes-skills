# Community Detection

"Community detection" is overloaded — different methods optimize different objectives and there is no universal definition of "community" in a network. This file is the decision framework for choosing among methods and the catalog of known pathologies.

## What "community" even means

At least four operational definitions are in active use:

1. **Modularity-based** (Newman & Girvan 2004): communities are sets of nodes with more internal edges than expected under a degree-preserving null model. *Louvain, Leiden, fast greedy*.
2. **Generative/inferential** (Karrer & Newman 2011; Peixoto 2014): communities are blocks in a Stochastic Block Model whose parameters are inferred from data. *graph-tool's SBM and nested SBM*.
3. **Dynamical / flow-based** (Rosvall & Bergstrom 2008): communities are regions where a random walker spends a long time before leaving. *Infomap, map equation*.
4. **Density-based / k-clique percolation** (Palla et al. 2005): communities are unions of overlapping k-cliques. *Cfinder*. Useful when overlap is the point.

These can give very different partitions. They are not approximating the same underlying truth.

## The pathologies of modularity

Modularity Q = (1/2m) Σ_ij [A_ij − k_i k_j / 2m] δ(c_i, c_j) has known and serious problems:

### Resolution limit (Fortunato & Barthélemy 2007)

Modularity cannot detect communities smaller than √(2m) edges. In a network with 1 million edges, communities under ~1,400 internal edges are invisible. Two real communities will be merged if either is too small. This is a *mathematical property* of the objective, not a bug.

### Degeneracy (Good, De Montjoye & Clauset 2010)

The modularity landscape has *exponentially many* near-optimal partitions, structurally very different from each other. A single Louvain run returns one of these almost arbitrarily; running again gives a different one. Without ensemble methods or stability analysis, modularity-based partitions are not reproducible.

### Overfitting (Lancichinetti & Fortunato 2009)

Modularity finds high-Q "communities" in Erdős–Rényi random graphs that have no community structure. Conclusion: a high modularity score *does not* establish that real communities exist. Compare to a configuration-model null.

### Louvain disconnects communities (Traag, Waltman, van Eck 2019)

The local-move + aggregation procedure can produce internally disconnected "communities" because nodes can move out of a community without checking whether the remaining nodes still form one. **Leiden** was developed specifically to fix this; it guarantees connected communities and additionally provides a refinement step that finds better local maxima. Use Leiden instead of Louvain by default.

### Modularity over-merges (resolution limit) AND over-splits (in heterogeneous graphs)

Different parts of the network have different "natural" community sizes; a single resolution parameter cannot fit both. The **Constant Potts Model (CPM)** in Leiden gives a tunable resolution parameter γ that avoids the resolution limit (Traag, Van Dooren & Nesterov 2011), and you can scan γ to get a hierarchy.

## Stochastic Block Models (the principled alternative)

SBMs (Holland, Laskey & Leinhardt 1983) model networks as generated by a process where each node has a latent group label, and edge probabilities depend only on the pair of group labels. **Karrer & Newman (2011)** introduced the degree-corrected SBM (DC-SBM) which controls for degree heterogeneity (without DC, SBMs put all high-degree nodes in their own block).

### Why SBMs beat modularity for "real" community detection

- **Generative**: you can simulate from the fitted model and check fit
- **Principled regularization** via Bayesian / minimum description length (MDL) inference (Peixoto 2017): the number of communities is *learned*, not chosen
- **Resists overfitting**: MDL penalizes complexity; an Erdős-Rényi graph correctly returns a single block
- **Handles assortative AND disassortative structure**: modularity only finds assortative; SBMs find blocks of any pattern (core-periphery, bipartite-like)
- **Hierarchical / nested versions** (Peixoto 2014) discover hierarchy automatically

### Practical SBM use

graph-tool is the canonical implementation (Peixoto). Minimal recipe:

```python
import graph_tool.all as gt
g = gt.load_graph("data.graphml")
state = gt.minimize_nested_blockmodel_dl(g)  # nested DC-SBM
state.draw()  # hierarchy plot
# blocks at each level
for i, s in enumerate(state.levels):
    print(f"level {i}: {s.get_nonempty_B()} blocks")
```

For Python without graph-tool, see `sbm` package or `pysbm`. R has `blockmodels` and `sbm` packages.

### Disconnected SBM communities (recent finding)

Park et al. (2024) and follow-ups: even SBMs can produce internally disconnected blocks. The **Connectivity Modifier** post-processes any clustering to enforce connectedness. Worth running when downstream interpretation requires connected communities.

## Infomap and the map equation

Rosvall & Bergstrom (2008): minimize the description length of a random walk on the network. Communities are regions where a walker is trapped for a long time.

- Best choice when the substantive process is **information flow** or **diffusion** (the implicit walk model matches reality)
- Handles **directed** networks naturally; modularity for directed graphs has multiple ad-hoc generalizations, none ideal
- Implementation: `infomap` Python package, `igraph::cluster_infomap`

The map equation has its own resolution limit (Kawamoto & Rosvall 2015), milder than modularity's, with a different functional form.

## Overlapping communities

If a node can belong to multiple communities (nearly always true in social data), modularity and standard SBM force a hard partition that misrepresents reality. Options:

- **Clique percolation (CPM, Palla 2005)**: communities = unions of adjacent k-cliques. Tunable k. Implementation: `cdlib`.
- **BigCLAM** (Yang & Leskovec 2013): generative overlapping community model, scales to millions of nodes
- **Mixed-membership SBM** (Airoldi et al. 2008): each node has a distribution over blocks
- **Link clustering** (Ahn, Bagrow & Lehmann 2010): cluster *edges* instead of nodes; nodes inherit multiple memberships through their edges. Very natural for social networks.

## Hierarchical / multiscale community structure

Almost all real networks have nested community structure (communities within communities). Plain modularity returns a single scale.

- **Nested SBM** (Peixoto 2014): infers hierarchy directly; default in graph-tool
- **Hierarchical Random Graph** (Clauset, Moore & Newman 2008): MCMC over dendrograms; useful for missing-link prediction
- **Leiden / Louvain at multiple resolutions**: scan the resolution parameter γ from 0.1 to 10, plot the number of communities; plateaus suggest "natural" scales (Reichardt & Bornholdt 2006)
- **Hierarchical link clustering** (Ahn et al. 2010): dendrogram of edge-similarities, cut at any height

For a serious hierarchical analysis, the nested SBM is the gold standard now.

## Bipartite communities

Standard methods on a bipartite projection are problematic (the projection inflates clustering and creates false communities — see the backbone section in `data_decisions.md`). Better:

- **Bipartite modularity** (Barber 2007): adapted modularity for two-mode networks
- **Bipartite SBM** (graph-tool supports it natively): `gt.minimize_nested_blockmodel_dl(g, state_args=dict(deg_corr=True, pclabel=g.vp.kind))`
- **Co-clustering / biclustering**: methods like LBM (Latent Block Model) simultaneously cluster rows and columns of the incidence matrix

## Comparing partitions

When you've run multiple algorithms (or one algorithm many times), compare partitions:

- **Normalized Mutual Information (NMI)**: 0 = independent, 1 = identical. Standard but biased high for many small clusters; use **adjusted NMI** (Vinh, Epps & Bailey 2010) for fair comparison
- **Adjusted Rand Index (ARI)**: 0 = chance, 1 = identical. Less sensitive to cluster count
- **Variation of Information (VI)** (Meilă 2003): a true metric; lower is more similar

Report partition stability as "mean ARI across 100 Louvain runs = 0.72" or "the dominant partition appears in 84/100 runs." A single run is a single sample from a distribution.

## Validation: did you find anything real?

Before reporting communities, validate:

1. **Null comparison**: shuffle the graph (configuration model preserves degrees), rerun the same algorithm. If modularity / map-equation score on the real graph isn't substantially better than on the null, the communities aren't real.
2. **Stability**: rerun with different seeds, different starting partitions. Stable communities are more trustworthy.
3. **Robustness to perturbation**: bootstrap the edges (sample with replacement, or randomly add/remove ε fraction); recompute. Stable nodes have low "consensus distance".
4. **Resolution**: scan the resolution parameter; communities that appear across a range of γ are real, communities that only appear at one γ are artifacts.
5. **Ground-truth comparison** (rarely available, often misleading): if metadata cluster labels exist, compute NMI between metadata and detected. But — Peel, Larremore & Clauset (2017) ("the ground truth about metadata and community detection in networks") showed that metadata are *not* a reliable ground truth; algorithms and metadata are answering different questions.

## Default recommendations

| Situation | Recommended algorithm | Library |
|---|---|---|
| Quick exploration, < 100k nodes, you want defensible partition | **Leiden** with modularity | `leidenalg` (Python) or `igraph::cluster_leiden` (R) |
| Want hierarchy, want principled K selection | **Nested SBM** | `graph-tool` |
| Directed network where flow matters | **Infomap** | `infomap` (Python) |
| Overlapping communities | **CPM** or **link clustering** | `cdlib`, custom |
| Very large network (>1M nodes) | **Leiden** with CPM, or label propagation | `graph-tool`, `cugraph` |
| Heterogeneous communities (some small, some large) | **Leiden+CPM** with γ scan, or **nested SBM** | `leidenalg`, `graph-tool` |
| Bipartite | **Bipartite SBM** (graph-tool) | `graph-tool` |
| Want statistical significance | **SBM with MDL** | `graph-tool` |

## Common mistakes

- Reporting Louvain's single output as "the" communities (run many; report stability)
- Using modularity on a bipartite projection (use bipartite SBM or Barber's bipartite modularity)
- Confusing **disjoint** with **non-overlapping** when ground truth has overlap
- Treating community labels as meaningful identifiers across networks (they're not — Community 1 in Network A has no relation to Community 1 in Network B)
- Reporting Q values without comparison to null
- Concluding "no community structure" when the algorithm failed; modularity may have resolution-limit blindness, not "no structure"
